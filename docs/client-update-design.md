# 客户端更新方案与实现

状态：代码已实现，本机自动验证通过；生产签名配置及真实平台升级验证待发版前完成。镜像按用户最新要求优先公开源，gpp.hydroroll.team、ghproxy.hydroroll.team 放在 ghproxy.net 后面兜底。
基线：`upstream/dev` 的 `1343cb3`，工作分支 `feature/client-in-app-update`。

## 已确认需求

- 本次只支持正式客户端，跟随 upstream 正式 Release；Debug 更新后续处理。
- 启动后和打开设置时自动检查；用户点击后才下载并应用。
- 有未保存内容或相关运行任务时可以下载，但要等用户保存、任务完成后再应用。
- 新版兼容当前原生程序时，保持原窗口打开，在窗口内短暂加载、刷新页面，让新版界面生效。
- 新版不兼容当前原生程序时，显示“正在重新启动客户端”对话框，然后自动重启加载完整新版；不要求用户手动重新打开程序。
- 重启提示是状态说明，原始更新操作已经由用户点击发起；无需再增加一轮相同的重启确认。下载、校验和更新等待条件都通过后，才进入此阶段。
- 用户选择经 GitHub Release 镜像下载，并委托选择几个公开镜像，按列表逐个尝试；候选顺序和 GitHub 直连兜底列入本次整体方案。
- Windows、macOS、Linux AppImage 支持完整自动更新；Linux deb 支持兼容界面热更新，需要完整升级时引导用户下载安装包，并展示签名清单里的 SHA-256，供用户下载后、安装前核对。
- 更新后恢复原工作区以及已保存的模板或字效会话，预览保持暂停；不恢复播放进度、撤销历史等临时状态。未保存内容仍阻止应用更新。

## 已核实事实

- 设置页已有版本号和构建校验码：`client/src/features/settings/PluginSettings.tsx`；版本来自 `client/src/lib/version.ts` 与 Vite 构建注入。
- 已发布的 0.9.5 只加载随包前端资源，没有运行时下载和切换前端资源的机制；首次启用该能力需要先安装包含资源更新机制的客户端。
- 前端刷新不替换 Rust 程序。模板保存、本机视频读取、聊天历史存储等仍通过当前进程已注册的原生命令执行。
- Windows 生产页面使用编译资源提供的回环 HTTP 服务，权限限定实际绑定的 URL；其他平台使用 Tauri 资源加载。热更新需要补充生产资源加载机制，并验证来源及预览 SDK 路径兼容。
- 模板、设置、未发送消息及部分参数草稿保存在页面内存；当前页面切换刻意保持业务工作区挂载。不能仅检查当前可见页是否有未保存内容。
- 字效会话有本地持久化和事件恢复基础，但后台会话也可能有任务；不能仅检查当前会话。服务端任务断线后状态不明时，不能当作任务已完成。
- 现有 Release 只提供安装包和变更日志，尚未发布更新清单、资源更新包或更新签名。
- 官方 Tauri Linux 整包更新使用 AppImage；本次 deb 已选择升级引导。Windows 全机安装及受保护目录可能需要系统授权，不能承诺绕过操作系统权限提示。

## 已批准方案

### 版本与兼容判断

- 设置页展示当前生效版本、可用版本和更新状态；详细信息区区分界面版本与原生程序版本，避免热更新后把旧原生程序误报为完整新版。
- 热更新必须有可靠的兼容证据。实现比对正在运行的原生程序与目标资源包的兼容指纹，并验证“旧原生程序＋新资源”的真实组合；不能只根据版本号新旧或与上一 Release 的差异判断。
- 原生输入至少覆盖 Rust 源码与生成协议、原生依赖和锁文件、Tauri 配置、构建脚本、权限、Info.plist、原生资源、相关构建配方和开关，以及实际锁定的 Tauri JS 桥接依赖。
- Rust 还编译进 `server/src/server/template/{fonts,sdk_catalog,motions}.json`，这些也是兼容输入，不能只监控客户端目录。
- 指纹规范化只能忽略项目自身的发版版本字段；第三方依赖版本、features 等继续参与判断。二进制本身嵌有前端，因此不能直接用整个二进制哈希判断可否热更新。
- 源码与配置指纹不等于语义证明；现有浮动工具链和系统依赖也需纳入构建证据及验证。缺少兼容证据时走完整更新。

### 应用时机与状态保护

- 下载阶段允许继续使用客户端。待应用时重新核查所有已打开工作区的未保存内容、正在保存或上传的操作，以及本客户端已知的未结束任务。
- 未发送的聊天文字和附图也属于需要保护的内容；不能因它们没有“保存”按钮就清空。保留等待状态，直到用户正常发送并等任务完成，或自行清空草稿；更新器不自动丢弃。
- 通过等待条件后，短暂禁止发起新编辑、提交和上传，防止核查完成后又产生新任务；保存必要的恢复位置，再刷新页面或开始完整安装。
- 应用更新过程要去重并互斥；关闭设置不能丢失下载状态。同一安装存在其他运行实例时，完整更新暂缓并提示用户处理，不能静默结束其他实例或在仍使用资源时删除资源。任务状态无法核实时保留等待状态，用户可以取消此次更新，不自动取消业务任务。

### 下载、验证与恢复

- 资源包、完整更新包和兼容元数据需要可信签名与完整性校验；更新来源与普通业务后端地址分开配置，不能让任意业务 API 地址替换客户端执行代码。
- 只使用已公开、附件齐全的正式 Release；同版本、旧版本、预发布或缺少本机产物的 Release 不当作可安装新版。超时或网络错误显示检查失败，不显示已是最新版。
- 下载与校验失败保留当前版本并允许重试；下载内容先保存到独立暂存位置，验证通过后才切换。解包要校验路径、文件类型和体积边界。
- 热更新保留上一份可用资源；新版启动未确认成功或加载失败时回退旧资源，避免白屏和反复自动更新同一坏包。回退要求持久数据仍能被旧界面读取，不能把资源回退当作任意数据迁移回滚。
- 镜像只负责传输，不构成更新信任来源；更新包和兼容元数据的可信度由内置公钥校验。版本检查也要能通过已选镜像完成，避免包可下载但仍因 GitHub API 不可达而无法检查版本。镜像失败、返回 HTML、缓存不同步或签名不匹配均不可跳过验证。
- 断电、手动退出或崩溃后，下次启动只加载已验证的可用版本；不读取半下载、半解包内容。
- 连续热更新始终对照实际原生版本；安装完整新版后优先使用与新版原生程序兼容且不旧于随包界面的资源，避免旧缓存覆盖新安装包。
- 整包更新使用各平台安装机制；前端资源回退与整包安装失败分开处理，不假设官方安装器自带通用自动回滚。下载安装失败或权限被拒时，明确提供重试/恢复路径。

### 发布与验证

- 复用现有正式 tag 构建和草稿 Release 完整性门禁，增加签名资源包、完整更新产物、兼容元数据和更新清单；产物齐全再对客户端开放。
- 首次正式启用前需要配置更新公钥与 CI 签名私钥 secret；私钥不进入源码、安装包或对话。镜像列表通过专用更新配置维护，提供默认顺序并允许构建或部署配置覆盖；不在各下载调用点散落域名。
- 必须验证真实桌面场景：兼容热更新窗口保持打开、完整更新提示后自动重启、未保存/后台任务等待、坏包拒绝、加载失败回退、连续及跨版本升级、断网与离线重开、平台权限和多实例冲突。
- 前端模拟测试、Rust 单元测试及发布脚本测试各自验证对应逻辑，不代替四平台安装与真实 WebView 验证。此文档尚不表示这些验证已执行或通过。

2026-10-16，在当前网络对 upstream 的正式 Release `v0.9.5` 做了三项只读测试：固定 tag 的完整 CHANGELOG、`releases/latest/download/CHANGELOG.md`、Windows 安装包的前 4096 字节 Range 请求。三个镜像的日志请求均返回 200，Range 请求均返回 206 且范围正确；内容 SHA-256 与 GitHub 直连结果全部一致，未返回 HTML。测试没有发送账号凭据、执行下载内容或下载完整安装包。

这验证了当前网络下的 URL 规则、小文件下载及 Range 响应，不证明长期稳定、全量大包速度、跨网络可用性或真实更新成功。本项目尚无更新清单和签名产物，因此本次未验证这些未来资产。

- 检查清单与下载资产共用这份源列表。按顺序有限尝试；连接失败、超时、非预期响应、HTML 错误页、清单格式错误或签名不通过时，拒绝该响应并尝试下一源。
- 版本检查遇到同版或旧版清单时继续尝试后续源，避免第一个镜像的旧缓存过早结束检查；不允许降低已确认版本，全部来源均无有效清单时显示检查失败。开始下载后按签名清单中的固定 tag 和资产标识请求，不再通过浮动的 latest 地址下载包。
- 连接与传输空闲超时分别设置，检查有整体时限；大安装包不复用本次探测的 10 秒限制。全部来源失败后保留当前版本并提供重试，不无限循环。
- 切换源不能把不同内容的断点直接拼接；首版可重新下载，只有能核对同一已签名资产时才考虑续传。自动下载内容的签名和体积校验由客户端执行，不依赖镜像站自报结果；deb 手动下载则按已签名清单展示摘要，供安装前核对。
- 默认列表可调整；不自动跟随网页上的新域名公告替换更新配置。公共站点没有可据以承诺的服务保障，失效时依靠列表回退及后续配置维护。

## 实现与发版配置

用户已批准实施。Rust `client/src-tauri/src/updates.rs` 负责检查、镜像切换、下载、签名校验、原子资源切换、失败回退及官方安装器调用；React 只负责设置展示、进度、草稿/请求门禁与恢复位置。`src-tauri/update-tools` 是 Rust 发布工具，与 `build.rs` 共用兼容指纹计算；没有新增 JavaScript 更新打包器。

- 更新资源是带入口校验的单个 JSON 文件（路径到 base64 内容），上限 64 MiB、4096 个文件，不解压归档。签名清单包含版本、目标平台、原生指纹、兼容验证标志及每个资产的体积、SHA-256、安装包签名；公钥只来自编译配置。安装包由官方 Tauri 更新插件验证版本绑定签名并安装。
- 运行时替换 Tauri 的 Assets；Windows 原有 localhost 服务继续经 AssetResolver 读取，并禁止缓存。Linux/macOS 继续使用原 Tauri 来源，并为资源响应设置 no-store。新版资源不混用旧文件；刷新不创建新窗口。
- `app_data_dir/updates/state.json` 保存当前/上一版、待确认标记和恢复位置。页面挂载后核对生效版本；60 秒未确认则回退，进程异常退出后的下一次启动也回退。失败版本不再热应用，转为整包更新或 deb 引导。多实例共享文件锁，应用时必须取得独占锁；不强行关闭其他客户端。
- 设置与聊天、模板草稿，业务对话框，上传/保存/读取请求，SQLite 中所有服务的未结束、未知状态或删除中会话参与门禁。等待可取消；取消不影响业务任务。最终核查前暂时锁交互，再次核查成功才应用。
- 恢复工作区、已保存模板及字效会话；不保存播放进度和撤销历史。业务 API 地址仍来自原设置，不能影响更新源或信任公钥。

首次启用前，在仓库 Actions 配置：

| 类型 | 名称 | 用途 |
| --- | --- | --- |
| Variable | `IMV_UPDATE_PUBLIC_KEY` | 官方 Tauri signer 生成的 `.pub` 文件内容，编译进每个平台客户端 |
| Secret | `TAURI_SIGNING_PRIVATE_KEY` | 对应私钥内容，只供正式 tag 构建签名 |
| Secret | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥口令；无口令时留空 |
| Variable（可选） | `IMV_UPDATE_MIRRORS` | 逗号分隔 HTTPS 前缀，空值使用已确认默认列表；末尾仍追加 GitHub 直连 |

用 `bun run tauri signer generate -w <仓库外的私钥路径>` 生成密钥并妥善备份；不要提交私钥。更新签名与 Windows 代码签名、macOS 公证是不同用途。普通构建未配置公钥时更新按钮禁用；正式 tag 缺少签名配置直接构建失败，不发布无法验证的更新。

发布工作流生成每个平台的 `update-<target>.json` 签名信封和 `resources-<target>.json`，以及两个 macOS `.app.tar.gz` 更新归档。连同原六个安装包与 CHANGELOG，共 17 个必需附件通过完整性门禁后才公开 Release。

### 热更新验证记录

`client/hot-update-validation.json` 初始为空，所有版本默认走完整升级。只有对目标平台做过“旧壳＋新前端”真实验证后，才登记以下结构（示意值不能直接照抄）：

```json
{
  "1.2.4": {
    "x86_64-unknown-linux-gnu": ["该组合实际构建的64位十六进制原生指纹"]
  }
}
```

原生指纹由 `build.rs` 计算，正式构建日志会输出，CI 同时通过 `IMV_UPDATE_METADATA_PATH` 把它传给 Rust 发布工具。记录必须同时匹配目标版本、平台及编译指纹，更新后的客户端还会再次比对自己真正运行的壳。登记文件自身不参与指纹。不要为了让热更新通过而手改指纹、关闭签名或把未经验证的组合标记为通过。

首次上线须先完整安装包含本机制的新壳；现有 0.9.5 无法自行热更新得到该机制。密钥轮换也需要规划完整升级，旧公钥无法验证直接换用新私钥的 Release。

### 验证范围

自动测试覆盖草稿与任务等待、请求互斥、取消、重启提示、坏签名/坏包、路径校验、Tauri AssetResolver 资源切换、跨实例锁、崩溃指针回退，以及 Rust 发布工具调用真实签名器生成四平台格式产物。测试只用临时测试密钥，模拟安装包绝不执行。

这些测试不等同于四个平台安装器和真实 WebView 升级通过。发布前仍须逐平台检查：窗口不关闭的热更新、预览/SDK、离线重开、连续升级及回退、完整更新的自动重启和权限提示，以及更新后恢复已保存内容；全部组合确认后才登记热更新验证记录。尚未配置生产密钥、运行 GitHub Release 工作流或发布更新附件。
